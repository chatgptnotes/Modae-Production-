# WinTrack Microsoft 365 integration plan

Status: proposed; no implementation or Azure configuration has been changed.

## 1. Recommended architecture and authentication flow

**Confirmed:** WinTrack is a React SPA served with its Express API from one Railway service. Connected login currently uses Supabase Auth passwords; the API verifies Supabase bearer tokens and active roster profiles. `@azure/msal-browser` exists only in the separate browser SharePoint module. There is no MSAL Node client or server Graph callback. See [`src/pages/Login.jsx`](../src/pages/Login.jsx), [`src/store.jsx`](../src/store.jsx), [`src/sharepoint.js`](../src/sharepoint.js), and [`src/server/app.ts`](../src/server/app.ts).

**Decision:** Configure Microsoft Entra as the login provider in each existing Supabase Auth project. Supabase continues issuing the WinTrack session JWT, so existing API authorization, roster IDs, and business storage remain in place. Require the configured tenant and an active, uniquely matched WinTrack roster profile before granting workspace access. Inventory and link existing password users to their verified Microsoft identities before cutting over; Supabase can link an OAuth identity to an existing verified-email account, but that result must be checked for each user. Retain legacy password behavior where needed for local/demo or transition, without offering it as connected production login. See [Supabase Azure login](https://supabase.com/docs/guides/auth/social-login/auth-azure) and [identity linking](https://supabase.com/docs/guides/auth/auth-identity-linking).

Use the **existing WinTrack Azure app registration** for both Supabase login and Express Graph access. Add its exact Supabase Auth callback and exact Express Graph callback as **Web** redirects. The supplied SPA redirects are not substitutes for either callback. Verify local, staging, and production origins before registration; never construct callbacks from an untrusted request `Host`. The server holds the confidential-client credential. A Supabase JWT is never sent to Graph.

For personal mail sending, Express starts a second, server-side Microsoft authorization-code flow after verifying the Supabase session. A one-time state binds the callback to that WinTrack user; the server checks the returned tenant and Microsoft identity against the user's linked Entra identity. MSAL Node acquires delegated `Mail.Send`. A server-only, per-user token cache can be held in the documented single Railway process for the first release; restart or token revocation prompts reconnection. Application tokens separately serve the approved SharePoint site and common mailbox. This may involve a brief Microsoft redirect when a user first connects mail, even though Microsoft SSO should usually avoid a second password prompt. See [Microsoft confidential-client flow](https://learn.microsoft.com/en-us/entra/msal/javascript/node/initialize-confidential-client-application).

## 2. Permissions and data flow

| Feature | Effective Microsoft permission | WinTrack enforcement |
| --- | --- | --- |
| Microsoft login | `openid`, `profile`, `email`; `User.Read` only if implementation actually calls Graph `/me` | Active roster profile, exact account binding, tenant check |
| SharePoint list, view, upload, move, delete | Application `Sites.Selected`, with a `write` grant on the one approved site | `canAccessPage(profile, 'folders', config)`, visible opportunity, fixed configured drive/root, and verified item ancestry |
| Common mailbox inbox and attachments | Scoped application `Mail.Read` | `canAccessPage(profile, 'inbox', config)`; dashboard preview only for users with that grant |
| Send from personal mailbox | Delegated `Mail.Send` | Active linked Microsoft identity, Inbox access, `leads.edit`, and access to the selected lead |
| Send from common mailbox | Scoped application `Mail.Send` | Same lead checks; mailbox address fixed on the server |

**SharePoint access decision:** WinTrack's current Documents grant governs project access. The server's selected-site application permission allows access even when the individual lacks a direct SharePoint grant. Individual SharePoint permissions therefore **are not preserved end to end**. This makes server checks mandatory for every item request. [`src/accessPolicy.js`](../src/accessPolicy.js) grants the `folders` page; [`src/workspaceAccess.js`](../src/workspaceAccess.js) projects visible opportunities. There is currently no separate document upload/delete action grant, so the first release applies the existing Documents page grant to those operations, preserving current behavior. `NON_SALES` remains submit-only.

Configure the exact **site ID, drive/library ID, and root folder ID** on the server. An opportunity ID determines its existing status/subfolder path; a requested file must resolve beneath that opportunity's root. The browser supplies an opportunity ID and an item ID, never an arbitrary Graph URL or drive ID. `Sites.Selected` requires an explicit site grant; current application `Files.ReadWrite.All` and `Sites.Read.All` are broader than this design needs. Remove them only after selected-site reads and writes pass in staging. See [Microsoft selected-site permissions](https://learn.microsoft.com/en-us/graph/permissions-selected-overview).

Files remain in SharePoint. Express streams authorized file bytes for download and PDF/image preview, with `private, no-store` responses and no persistent server copy. Word, Excel, and PowerPoint previews use the existing bounded Office-to-PDF conversion path or the existing workbook renderer where appropriate; conversion uses a temporary directory removed after processing. Verify LibreOffice availability in Railway. Other formats receive an authorized download. Do **not** return an application-authenticated Graph preview URL to the browser: Microsoft warns that anyone holding it acts with the application caller's permissions. Direct SharePoint `webUrl` opening cannot be relied on for users without individual SharePoint access. See the [existing converter](../api/_office-convert.js) and [Graph preview warning](https://learn.microsoft.com/en-us/graph/api/driveitem-preview?view=graph-rest-1.0).

The common mailbox is distinct from each user's mailbox. The Leads page shows a paged common inbox for review; the dashboard shows a limited project-mail summary only to users with Inbox access. Mail is **not** automatically converted into a lead. An authorized user links a message to a lead or opportunity; store the mailbox's immutable message identifier and link metadata in the existing `records` table through revision-aware server writes. Fetch mail bodies and attachments from Exchange when needed, without copying the whole mailbox into workspace state. Personal sending uses `/me/sendMail`; common sending uses `/users/{configured-mailbox}/sendMail`. A personal-address response to a message held only in the common mailbox preserves subject and context in WinTrack; exact Exchange conversation threading is outside the agreed first release. Graph `202 Accepted` means accepted for processing, not delivered. See [message listing](https://learn.microsoft.com/en-us/graph/api/user-list-messages?view=graph-rest-1.0) and [sendMail](https://learn.microsoft.com/en-us/graph/api/user-sendmail?view=graph-rest-1.0).

Use Exchange **Application RBAC** to scope effective application `Mail.Read` and `Mail.Send` to the common mailbox. The currently consented broad Entra `Mail.Read` application grant must be restricted or replaced as part of that setup; an overlapping unscoped Entra grant can defeat an RBAC scope. Add application send authority only when its mailbox restriction is ready. `AccessReview.ReadWrite.All` has no identified use. See [Exchange Application RBAC](https://learn.microsoft.com/en-us/exchange/permissions-exo/application-rbac).

### Backend route authorization contract

- **Microsoft connect/status:** Verify the Supabase token with `auth.getUser`, resolve an active profile through `activeProfile`, and bind OAuth state to that auth user. Callback accepts only an unused, unexpired state and the configured tenant/identity.
- **Documents list/content/upload/move/delete:** Repeat fresh profile lookup; require `canAccessPage('folders')`; confirm the opportunity is in the user's `projectWorkspace` projection; resolve every item under the configured site, drive, root, and opportunity folder. A guessed item ID or path cannot bypass those checks.
- **Common inbox/message/attachment:** Require `canAccessPage('inbox')`; the mailbox identifier comes only from server configuration. Dashboard callers receive a smaller projection through the same check.
- **Mail link and send:** Require Inbox access, `canPerform('leads.edit')`, and visibility of the selected lead. Use only the selected user's delegated connection for "my email"; use only the configured, Exchange-scoped application identity for "common mailbox." Never accept a browser-provided arbitrary `From` address.

This route contract closes the gap in [`src/pages/Folders.jsx`](../src/pages/Folders.jsx), where upload/delete controls currently depend on page UI, and preserves the existing Non-sales restriction in `effectiveAccess`.

## 4. Security risks and rollback

**Highest risks:** The current browser SharePoint module stores MSAL tokens and editable site configuration in `localStorage`; the first cached Microsoft account is not bound to the WinTrack account. Current SharePoint calls do not pass through WinTrack server authorization. A single Azure registration also means its confidential credential can exercise every granted application permission, making selected-site and Exchange mailbox scoping especially important. Keep that credential server-only and separate per environment.

The current `Mail.Read` application grant is potentially tenant-wide; do not enable the mail feed until its effective mailbox restriction is tested against both the allowed mailbox **and a disallowed mailbox**. The same applies to new application `Mail.Send`. Avoid logging tokens, upload URLs, mail bodies, attachment bytes, or provider error payloads. Treat Graph timeouts and `429` responses as retryable reads; for sends, do not automatically retry after an uncertain response because duplicate delivery is possible. Persist a WinTrack send-operation ID and result; on uncertainty, reconcile before offering a manual retry.

Roll out login while preserving current Supabase user IDs and business data. Do not remove existing password identities or browser file fallbacks until Microsoft login and file migration are proven for every affected account. Keep a deployable previous application build and an admin recovery path; Azure permission removal occurs last, after staging and production traffic has moved to the scoped paths. No database table migration is planned: mail-link metadata uses the existing `records` contract and `save_rows`.

## 5. Acceptance checklist

- A previously provisioned user signs in with Microsoft and retains the same WinTrack role, ownership, drafts, and account ID. An unrostered, inactive, wrong-tenant, or ambiguously matched user is denied.
- Local, staging, and production use their own exact callbacks and resources. An altered redirect, reused OAuth state, mismatched Microsoft identity, or expired connection fails safely.
- A Documents-authorized user can list, preview, stream, upload, move, and delete only within a visible opportunity's configured SharePoint root. A Non-sales user and a user denied Documents cannot use the API directly. A forged drive/item/path is rejected.
- PDF, images, Word, Excel, and PowerPoint open or download through authorized endpoints without persistent server files. Large/unsupported files produce a clear outcome; temporary conversion files are cleaned after success and failure.
- The common inbox pages correctly, displays messages and attachments only to Inbox-authorized users, and appears as a limited dashboard summary only for those users. A reviewed message can be linked once to the intended lead/opportunity; refresh and concurrent linking do not create duplicates or automatic leads.
- "My email" sends through the signed-in user's delegated token. "Common mailbox" sends through only the configured mailbox. The API rejects forged sender addresses and inaccessible leads. A Graph acceptance is recorded distinctly from delivery; uncertain sends do not automatically duplicate.
- Exchange tests prove that the application cannot read or send as an unrelated mailbox. SharePoint tests prove it cannot access an unselected site.
- Existing approvals, proposal email, local demo behavior, desktop/phone routes, and Supabase synchronization still work. Run `npm test`, `npm run build`, `git diff --check`, and the manual smoke checklist in staging before production.

## 6. Confirmed assumptions and remaining inputs

**Confirmed decisions:** SharePoint stores documents; Supabase keeps structured WinTrack records. Existing WinTrack page grants govern document access, including for users without direct SharePoint grants. Current role limits remain. Mail arrives in the Leads inbox for review before lead creation. Personal replies need best-effort subject/context continuity. Preview is required for Office documents, PDFs, and images; native CAD preview is not part of the first release. Use the existing single WinTrack Azure registration.

**Operational inputs still needed before configuration:** Actual tenant and app IDs, exact live origins and Supabase callback URLs, approved site/drive/root IDs for each environment, common mailbox identity, existing-user linking inventory, and an Exchange administrator able to apply and test mailbox-scoped application roles. These are tenant facts unavailable from the repository; they do not change the implementation approach above.
